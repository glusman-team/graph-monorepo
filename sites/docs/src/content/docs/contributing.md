## Set up

Use the default Nix development shell so Go, Node, BEAM, Python, and repository tools stay on the tested toolchain. CI and production use `nix develop .#deploy`, which excludes interactive Agent of Empires tooling.

```sh
direnv allow        # or nix develop
npm ci
make hooks
make test
```

Run heavy Linkouts builds and tests on the designated build host. Limit concurrent work to four CPUs there and never run them on a workstation that is being used interactively.

## Daily loop

1. Identify the owning component in the [architecture guide](../architecture/).
2. Keep changes inside that component unless a shared contract genuinely changes.
3. Run the narrow component checks, then the affected Nx targets.
4. Run contract fan-out whenever Go storage code, Phoenix reading code, or canonical fixtures change.
5. Review generated bytes and documentation links before committing.

Useful commands:

```sh
npx nx affected -t test
make dead-code-check
npm run docs:check
npm run docs:build
prek run --all-files --hook-stage pre-push
```

Component details live in each project README and the Linkouts operating guides.

## Safety rules

- Never commit `.env`, `.envrc`, Cosmos keys, Fly tokens, connection strings, or production data dumps.
- Never put credentials in Dagster run configuration, Pipes extras, asset metadata, or logs.
- Use file stores and fake engines for integration tests. Real Cosmos or Fly operations require a separate explicit deployment step and production authorization.
- `linkouts_upload` is manually triggered. Do not add a schedule or sensor without an approved design.
- Destructive definitions require `LINKOUTS_ENABLE_DESTRUCTIVE_JOBS=1` at code-location load and an exact target confirmation at execution.
- Keep the preview public and credential-free. It serves only the committed contract fixture.
- Do not weaken assertions, make vulnerability scans informational, or skip an applicable CI job to obtain a green result.

## Style and commits

Python uses Ruff with a 100-character line length. Go uses the module's formatters and linters. Phoenix uses `mix format` and strict Credo. Documentation uses Prettier, typed Starlight content, and generated-link checks. User-facing text is ASCII.

Use conventional commits such as `feat:`, `fix:`, `docs:`, `test:`, and `chore:`. See the repository `CONTRIBUTING.md`, `SECURITY.md`, and issue templates for the complete contribution and reporting process.
