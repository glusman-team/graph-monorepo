# DAKP release automation in Dagster (weekly build -> HF publish)

Status: ready for review. Decisions locked with the user:

- Friday 17:00 **America/Los_Angeles**, production host **wenceslaus** (Ubuntu 24.04 + Nix 2.18.1, 4x P100-16GB).
- "Track main" = preflight fetches `origin/main` and **fails loudly** on any drift; no self-updating code mid-run.
- **Fully automatic HF publication** (upload + prune + tag), older versions preserved by `v<version>` dataset tags. `DAKP_PUBLISH_DRY_RUN=1` for rehearsal.
- Supervision: **systemd user units generated by the Nix flake** (preferred over tmux/process-compose), linger enabled with sudo.
- GPU gate: launch only when **every card reports <= 1024 MiB used** (`nvidia-smi --query-gpu=memory.used`); hourly retries, 24h window starting Friday 17:00 (deadline Saturday 17:00).

## Context

DAKP releases are manual today: an operator sets `DAKP_PUBLICATION_VERSION`, runs
`dakp_build` by hand on wenceslaus, then follows the `release-dakp` skill (verify, stage,
`upload_folder`, hand-edit the card, prune, tag). Versioning is already decoupled from
pyproject (`DEFAULT_PUBLICATION_VERSION = "0.1.0"` in `tablassert.py`, overridden per run).
Target: a 24/7 Dagster deployment that every Friday 17:00 acquires sources (7-day freshness
gate kept), builds only when upstream data changed, auto-bumps the patch version from the
latest HF tag, generates the dataset card from the actual build outputs, publishes to HF,
and opens a populated GitHub issue on any failure. No crontab, no wrapper shell scripts
outside the dag project; everything is Dagster assets/jobs/schedules/sensors plus env vars.

| Canada Vigilance | "The data set is updated on a monthly basis" (zip Last-Modified 2026-10-21) | https://www.canada.ca/en/health-canada/services/drugs-health-products/medeffect-canada/adverse-reaction-database/canada-vigilance-online-database-data-extract.html | **30-day freshness gate** matching monthly publication; per-source override |
| ICD-10-CM Table of Drugs and Chemicals | Annual FY release plus possible April update. Parent currently has `2027/`; `2026-update/` contains an April table-and-index zip | https://ftp.cdc.gov/pub/Health_Statistics/NCHS/Publications/ICD10CM/ | Replace the pinned default with **latest-release autodiscovery** and a **7-day discovery-cache gate**; selected zips remain immutable/content-addressed |

Consequence: with a weekly cadence, DailyMed/Drugs@FDA/EMA will change most weeks; FAERS
and ICD-10-CM change rarely. Freshness behavior is standardized instead of being a
source-by-source special case:

- `DAKP_SOURCE_REFRESH=auto|cached|force`, default `auto`. `auto` applies the freshness
  gates above. `cached` performs **no source network access**, reuses cached artifacts
  regardless of age, and fails loudly naming any missing source cache. `force` rediscovers
  and redownloads. The scheduled release always uses `auto`; existing `DAKP_FORCE=1`
  remains the global cache/op-index bypass and implies `force` acquisition.
- Manual/on-demand `dakp_build` remains available unchanged. For a fast build outside the
  weekend, launch it with `DAKP_SOURCE_REFRESH=cached`; this avoids DailyMed downloads and
  even the FAERS/ICD-10-CM discovery requests. Narrow `dakp_build_<stage>` jobs continue
  to read published upstream refs without acquiring anything.
- `DAKP_SOURCE_MAX_AGE_DAYS=7` remains the shared default for fast sources. Source-specific
  env overrides map onto the existing fetcher params:
  `DAKP_DAILYMED_MAX_AGE_DAYS`, `DAKP_DRUGSFDA_MAX_AGE_DAYS`,
  `DAKP_EMA_MAX_AGE_DAYS`, `DAKP_EMA_DOCUMENTS_MAX_AGE_DAYS`,
  `DAKP_FAERS_MAX_AGE_DAYS`, `DAKP_ICD10CM_MAX_AGE_DAYS` (default 7),
  `DAKP_EMA_SMPC_MAX_AGE_DAYS` (default 30), and
  `DAKP_CANADA_VIGILANCE_MAX_AGE_DAYS` (default 30). A non-positive value means "always re-check
  upstream"; `cached` is the explicit no-network mode.
- FAERS cached-only mode enumerates existing `faers/faers_ascii_<Q>.zip` aliases instead
  of fetching the index. Auto mode reuses a content-addressed index/discovery snapshot
  until its 7-day gate expires, then runs the existing quarter discovery; newly discovered
  quarters are downloaded, existing quarter zips are reused.
- ICD-10-CM discovery parses the CDC parent listing, ranks fiscal-year releases and an
  April update within the same FY, ignores committee/presentation directories, then finds
  the table-and-index zip despite historical space/hyphen/April filename differences.
  Zero or ambiguous candidates fail loudly; there is no silent fallback to an older FY.
  `DAKP_ICD10CM_URL` remains an explicit pin for tests/reproducibility. The selected FY,
  URL, retrieval date and BLAKE3 are persisted with the acquisition and consumed by
  `extract_icd10cm`, `icd10cm_screen.py`, `tablassert.py` (RIG), the delta message and the
  card, replacing the hardcoded FY2027 constants in the build path. Checked-in offline
  snapshots are not auto-edited.

## Approach

Two jobs plus sensors, so "no upstream change" never starts a build and never bumps a
version:

```
Fri 17:00 schedule -> dakp_release_check  (preflight + acquire_* + source_delta)
                          |
                          v (only if delta non-empty, and not already consumed)
        gpu_gate_sensor (hourly, <=24h window)  -- nvidia-smi free? -->
                          |
                          v
        dakp_release_build (in-process executor)
          preflight -> extract_* -> shape_* -> tablassert_configs -> kg_build
          -> kg_qc -> release_verify -> dataset_card -> hf_publish
                          |
        run_failure_sensor (both jobs) -> GitHub issue from template
```

1. **`dakp_release_check`** (scheduled, cron `0 17 * * FRI`, `execution_timezone`
   `America/Los_Angeles`, overridable via `DAKP_RELEASE_TIMEZONE`):
   `release_preflight` validates every input before work starts - `DAKP_FULLMAP` exists and
   is readable, `DAKP_EXTRACT_WORKER_BIN` exists, `HF_TOKEN` + `GITHUB_TOKEN` present and
   accepted by their APIs, repo ids valid, disk headroom on the workdir/published filesystems,
   `DAKP_NER_OFFLINE` unset, no `DAKP_QUARTER_LIMIT`/`DAKP_RELEASE_LIMIT`,
   `DAKP_SOURCE_REFRESH=auto`, the managed NER-cache daemon healthy when required, and
   `git fetch origin main` + `git rev-parse HEAD == origin/main` (any drift fails the run
   loudly, which also exercises the failure-issue path) - then the existing
   `acquire_*` assets run with the standardized source policies above, then `source_delta`
   fingerprints each source's acquired refs (sorted BLAKE3 ids + upstream
   `last_modified`/`retrieved_at` from the artifact manifests) and diffs against the last
   published release's fingerprints.
   Empty delta -> run ends successfully with `changes=0`, nothing else happens.
2. **`gpu_gate_sensor`** (`@dg.sensor(job=dakp_release_build, minimum_interval_seconds=3600)`):
   finds the latest successful unconsumed `dakp_release_check` run whose delta is non-empty
   (cursor holds the consumed run id + the window deadline = check-run start + 24h, i.e.
   Saturday 17:00 for an on-time Friday tick). Gate: `nvidia-smi --query-gpu=index,memory.used`
   must show **<= 1024 MiB used on every card** (`DAKP_GPU_MAX_USED_MIB=1024`, device set from
   `nvidia-smi -L`); `--query-compute-apps` output is logged for diagnosis and a missing
   `nvidia-smi` fails the tick loudly. When the gate passes it emits one `RunRequest`
   (`run_key` = check run id, so retries cannot double-launch) tagged with the next version.
   Past 24h it skips with a reason and files one "GPU never freed" issue instead of building.
3. **Version**: at build launch, `HfApi.list_repo_refs(repo_type="dataset")` tags matching
   `v<semver>` -> max -> patch+1 (e.g. `v1.27.0` -> `1.27.1`). Passed as run tag
   `dakp/publication_version`; `run_config()` gains an override so every stage embeds it
   (RIG, KGX stem). pyproject untouched. Publish re-asserts `v<new>` and `<new>/` do not
   already exist, so a race cannot overwrite a release.
4. **`dakp_release_build`**: reuses the existing asset graph verbatim from `extract_*`
   through `kg_qc`, then adds `release_verify` (tablassert `validate-kgx` + screened-CURIE
   check on the published pair), `dataset_card`, `hf_publish`. Executor:
   `dg.in_process_executor` set on the job itself, replacing the external
   `dagster-inprocess.yaml`.
5. **Dataset card** (`dataset_card` asset): computed from actual outputs only - node/edge
   counts, predicate and category tables, namespaces, taxon counts parsed from the
   published ndjson pair; bytes + MD5 per file; biolink version from the generated RIG;
   `tablassert validate-kgx` result; qc.json. Releases table = previous card's rows
   (fetched from HF) + the new row. New "Build process" section describes the automated
   weekly Dagster release. "What changed in <version>" is the pregenerated delta message:
   `New data for N sources on <dates>` plus one bullet per source (source, upstream
   last-modified/retrieval date, new artifact count) and node/edge deltas vs the previous
   release. Static prose (schema fields, sources, license, loading snippets) lives in one
   template with the version/counts interpolated.
6. **`hf_publish`**: the runbook order from `release-dakp`/`publish.py`, as Python
   (`huggingface_hub`, already in the venv): upload `<version>/` (ndjson pair + RIG) ->
   commit the generated README -> prune superseded dirs only after their `v<old>` tag is
   confirmed -> create `v<new>` -> verify by re-downloading and comparing MD5. Only after
   success does it write the new fingerprints into the release state file, which is what
   makes the next week's delta comparison correct. `DAKP_PUBLISH_DRY_RUN=1` stages
   everything and logs the plan without mutating HF.
7. **Failure issues**: `.github/ISSUE_TEMPLATE/dakp_build_failed.md` plus a
   `@dg.run_failure_sensor(monitored_jobs=[both jobs])` that fills the template: job, run
   id + Dagster UI URL, git sha, failed step(s), error type/message (truncated), per-step
   start/end/duration table from `instance.all_logs(run_id)`, source-delta summary, GPU
   snapshot, and a truncated log tail in a `<details>` block. Dedup by fingerprint
   (job + step + first error line): repeat failures comment on the open issue instead of
   opening duplicates. GitHub REST via httpx/requests with `GITHUB_TOKEN` (no `gh` CLI on
   wenceslaus).
8. **Model lifecycle**: keep the existing lazy `MiningPool` (no pool on all-cache-hit runs,
   workers exit via `dispatch_pool`), add an explicit `DiseaseNER.close()` releasing the
   model + per-device flock fd and calling `torch.cuda.empty_cache()`, invoked in a
   `finally` around each `_run_shape`, and a post-build GPU check that logs any process
   still holding memory after the run. GPU free-memory gate before mining prevents
   competing with the resident llama-server.
9. **24/7 runtime**: `dagster.yaml` for the production instance (QueuedRunCoordinator
   `max_concurrent_runs: 1`, run_monitoring with start/cancel timeouts and
   `free_slots_after_run_end_seconds`, tick retention). Supervision = three **systemd user
   units generated by the flake** (`nix/modules/dagster.nix` gains a `dagster-units`
   package emitting `dagster-daemon.service` + `dagster-webserver.service` +
   `dakp-nercache.service`, `Restart=always`,
   `EnvironmentFile=%h/.config/dagster/dagster.env`); install with `nix build`,
   `systemctl --user link/enable --now`, and one-time `sudo loginctl enable-linger sgoetz`
   so the services survive logout and reboot. The units' ExecStart is the existing
   nix-generated launcher (cd `$DAKP_REPO_ROOT/dagster/deployments/local`, set `DAGSTER_HOME`,
   `uv run dagster-daemon run -w ../../workspace.yaml` / `dagster-webserver`); no new shell
   scripts are added to the repo. Schedules and sensors default to RUNNING only when
   `DAKP_RELEASE_ENABLED=1`, so a dev checkout never auto-publishes.
10. **Release state**: `$MO_PUBLISHED_ROOT/dakp/release/state.json` holds the last published
   version + per-source fingerprints, written only after a successful HF publish. Missing
   state (first automated run) means "treat every source as changed", i.e. build, never
   silently skip. Deleting the file is the documented way to force a release.
11. **NER-cache daemon**: reuse the existing Go/Pebble `dakp-nercache` server rather than
   adding a new database. The flake gains a `dakp-nercache` `buildGoModule` package
   (`cmd/dakp-nercache`, pinned `vendorHash`) and `dagster-units` emits a third unit,
   `dakp-nercache.service`, with `Restart=always` and the same `EnvironmentFile`. It runs
   `dakp-nercache --workdir $DAKP_WORKDIR`, stores Pebble under
   `$DAKP_WORKDIR/cache/ner/`, and publishes the existing `server.json` (`pid`, ephemeral
   localhost port). Dagster units declare `Wants=`/`After=dakp-nercache.service`.
   `MentionCache` already discovers and reuses that live server; add
   `DAKP_NERCACHE_EXTERNAL=1` for the systemd deployment so the client waits for the
   managed endpoint during restarts and **never spawns a competing server** against the
   single-owner Pebble lock. Development keeps the current lazy-spawn/fail-soft behavior.
   `DAKP_NERCACHE_REQUIRED=1` makes release preflight fail if `/health` is unavailable;
   `/stats` and the selected cache URL go into run metadata/logs. Clean shutdown still
   removes `server.json`; stale PID/health checks already handle crashes.

New env knobs (all optional except the secrets and `DAKP_FULLMAP`, which already exists):
`DAKP_RELEASE_ENABLED`, `DAKP_PUBLISH_DRY_RUN`, `DAKP_RELEASE_TIMEZONE`,
`DAKP_RELEASE_CRON` (default `0 17 * * FRI`), `DAKP_GPU_MAX_USED_MIB` (1024),
`DAKP_GPU_GATE_HOURS` (24), `HF_TOKEN`, `DAKP_HF_REPO_ID` (`SkyeAv/drug-approvals-kp`),
`GITHUB_TOKEN`, `DAKP_GITHUB_REPO` (`glusman-team/graph-monorepo`),
`DAKP_REPO_ROOT` (git main check), `DAKP_DAGSTER_URL` (links in issues),
`DAKP_SOURCE_REFRESH` and the per-source freshness overrides listed above,
`DAKP_NERCACHE_EXTERNAL=1` and `DAKP_NERCACHE_REQUIRED=1` in production. Existing knobs
(`DAKP_FULLMAP`, `DAKP_WORKDIR`, `MO_PUBLISHED_ROOT`, `DAKP_SOURCE_MAX_AGE_DAYS=7`,
`DAKP_ICD10CM_URL`, `DAKP_NERCACHE_BIN`, `DAKP_NERCACHE_STARTUP_TIMEOUT`,
`DAKP_THREADS`, `DAKP_MEMORY_BUDGET_GB`, `DAKP_EXTRACT_WORKER_BIN`) are reused.
